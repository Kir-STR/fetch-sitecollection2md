# Идея: fetch-sitecollection2md

## Что хочу

Простой инструмент, который собирает коллекцию с сайтов-каталогов в md-файл.

Примеры источников:

- витрины «made with / awesome»: madewithjev.com, shipwithjev.com, awesomejev.com, madewithlaya.com;
- каталоги MCP: mcp.so, smithery.ai, glama.ai/mcp, PulseMCP;
- cookbook-репозитории Anthropic и OpenAI;
- Vercel Templates;
- коллекции на Replicate;
- коллекции на GitHub (awesome-списки, topics).

Это **не универсальный** инструмент на все случаи жизни, а **ядро + плагины/скрипты**, адаптированные
под конкретную коллекцию.

## Цель

Искать потенциальные **wedge** — узкие задачи, с которых можно зайти продуктом (приложение, бот, расширение).
Дальнейшее (проверка поискового спроса, реализация) — вне этого инструмента.
Ядро общее и простое; адаптеры — просто скрипты. **Потребитель md-файла — агенты**, не человек.

## Результат

md-файл с перечнем, удобным для анализа. По каждой записи зафиксировано:

- **job** — ключевая задача, которую решает запись;
- **краткое описание**;
- **источник**;
- **комментарий**.

## Решения (обсуждение 2026-09-25)

- Инструмент делает только **fetch**: собирает сырые записи. Без LLM.
- Job, связи, анализ — отдельная задача вне инструмента (агент по готовому сырью). Enrich сейчас не делаем,
  даже в виде промпта.
- Формат — для агентов. Человеку при необходимости — отдельный скрипт md → html-таблица.
- Повторный запуск — **снимок с датой**: `<collection>/YYYY-MM-DD.md`, старые снимки не трогаем.
  Сравнение снимков показывает новые записи и рост сигналов. Ядро не сливает, только пишет новый файл.
- Снимки пишутся в `!all/data/my/tools/fetch-sitecollection2md/<collection>/`. Инструмент S3 не знает;
  бэкап — позже, строкой в `vault-confs/data-sync.tsv` (`rclone sync --backup-dir`, удаление локально
  переезжает в `trash`).
- Стек — Node (ESM, JS без сборки), ядро без зависимостей (встроенный `fetch`). Браузер в ядро не входит;
  если источник без JS не отдаёт данные — `playwright` внутри конкретного адаптера.
- Разведка SPA-источников при написании адаптера — `chrome-devtools-mcp` (`list_network_requests` /
  `get_network_request`) как помощник агента, не зависимость. browser-harness (Python, LLM в рантайме) — нет.
- Снимок — пара файлов с одинаковыми записями: `YYYY-MM-DD.md` (агенту) и `YYYY-MM-DD.jsonl` (скриптам
  сравнения снимков). Поля записи: `title`, `url` (ключ), `source`, `description` (как на сайте), `tags`,
  `signal` (число + единица), `extra` (специфика источника). Job и комментарий — не в fetch.
- Линза — **готовые решения, которые люди публикуют** (made-with витрины): за ними стоят наболевшие задачи.
  MCP-каталоги (mcp.so, smithery, glama, PulseMCP) на старте не рассматриваем — другая линза. Glama к тому же:
  ~92k записей, API только с ключом и лицензией с атрибуцией, `/api/` закрыт в robots.txt.
- **v1 — 4 источника разной механики:**
  - madewithlaya.com — SSR-HTML, 115 записей, пагинация `/page/N` / `sitemap.xml`;
  - awesomejev.com — статический HTML, 1 094 записи, ★ звёзды, язык, repo/site;
  - n8n templates — JSON API `api.n8n.io/templates/search`, 12 570 записей, `totalViews`, `price`
    (у `api.n8n.io` в robots `Disallow: /` — принято: снимки редкие, с паузами);
  - replit.com/gallery — `__NEXT_DATA__` + страницы категорий, ~154 записи, `viewCount`, `remixCount`
    (курируемая витрина Replit).
- **Бэклог источников:** madewithbolt.com (первым; SSR, robots открыт), madewithjev.com (729, всё на главной),
  shipwithjev.com, Zapier Templates, Product Hunt (API с токеном), Hugging Face Spaces (публичный API, likes),
  There's An AI For That, Gumroad Discover, Make templates (Cloudflare), Vercel Templates, MCP-каталоги,
  cookbook-репо Anthropic/OpenAI, коллекции Replicate и GitHub. Bolt.new Gallery публичной коллекцией не является
  (`/gallery` → чужой проект в `/~/`).
- Для поиска wedge ценны сигналы популярности (звёзды, установки, запуски, upvotes) — брать, если источник отдаёт.

## Открытая проблема: связи

Job'ы будут пересекаться: одну и ту же задачу можно решить с помощью jev так, а с помощью n8n — иначе.
Пока непонятно, как управлять такими связями без оверинжиниринга.

## Первые соображения (для обсуждения)

- **Источники неоднородны.** Одни отдают JSON/API (smithery, glama, Replicate, GitHub), другие — HTML
  (made-with витрины), третьи — markdown в репо (cookbook, awesome-списки). Отсюда естественная граница
  «ядро / плагин»: плагин умеет только достать сырые записи своей коллекции, ядро — всё остальное.
- **Job почти никогда не лежит на сайте готовым.** Сайт даёт название и описание; job — это интерпретация.
  Её формулирует человек или LLM. Это самая дорогая и самая ценная часть — и главный вопрос дизайна.
- **Связи можно не хранить явно.** Если job записывается из контролируемого словаря (короткий slug,
  например `pdf-to-structured-data`), то «одна job — разные инструменты» получается группировкой по slug,
  без графа и без базы. Словарь — отдельный md-файл, который растёт по мере сбора.
- **Повторный запуск.** Коллекции обновляются. Ручные поля (job, комментарий) не должны затираться
  при повторном сборе — значит, нужен стабильный ключ записи (обычно URL) и слияние, а не перезапись.
